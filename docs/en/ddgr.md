# DuckDuckGo HTML endpoint — 202 blocking field report

Status: live, primary source for the v0.1.0 rate-limit guard ([§8 of the spec](spec.md#8-rate-limiting)).
Last measured: 2026-05-08 18:05–18:20 KST.
Egress: AS9318 SK Broadband (Seoul, KR), residential consumer IPv4.
Endpoint: `https://html.duckduckgo.com/html/`.
Client profile: `wreq` 5.3 with `EmulationProvider::default()` (Chrome 136-shape JA3/JA4),
no `User-Agent` header, in-memory cookie jar, redirect policy `none`.
Request body (form-encoded): `q=rust+programming+language`, `b=`, `df=`, `kf=-1`, `kh=1`,
`kl=us-en`, `kp=1`, `k1=-1`.

All probes were generated by `cargo run --example ddg_probe --release`. Raw JSONL events
for each scenario are stored in your local cache only and are not committed to the repo;
the summary numbers below were extracted from those runs.

This document supersedes the speculative "ddgr field report" referenced in earlier spec
revisions. The previous numbers ("≤20s recovery silent, ≤60s probing, 50-parallel
threshold") were imported from the upstream `jarun/ddgr` issue tracker without primary
measurement; the section below replaces them with a first-party characterization.

---

## 1. What "blocked" looks like on the wire

A blocked request returns `HTTP 202 Accepted` (not `429`, not a redirect) with a 14.0–14.2
KiB HTML body. The body contains the DuckDuckGo CAPTCHA modal:

```html
<title>DuckDuckGo</title>
…
<form id="challenge-form" action="//duckduckgo.com/anomaly.js?…" method="POST">
  <div class="anomaly-modal__title">Unfortunately, bots use DuckDuckGo too.</div>
  <div class="anomaly-modal__description">Please complete the following challenge to confirm this search was made by a human.</div>
  <div class="anomaly-modal__instructions">Select all squares containing a duck:</div>
  …
</form>
```

Key static markers usable by the parser to classify a `200`-response anomaly page (which we
also observed historically) and the `202` page consistently:

- `class="anomaly-modal__*"` (modal root, title, description, image, …)
- `id="challenge-form"`
- `Unfortunately, bots use DuckDuckGo too.`
- `action="//duckduckgo.com/anomaly.js?…"`

The `crates/duckduckgo-core/src/parser/block.rs` classifier already covers `202` status and
`anomaly_modal` body markers; no change is needed to detect a block.

`HTTP 403` and `HTTP 429` were **not** observed in this round (KR/SK Broadband, Chrome-shape
TLS, empty UA). The block is universally `202` here. We keep `403`/`429` classification in
the code as a defensive signal for other egress profiles.

## 2. Burst tolerance from a cold IP

Method: each row is one round of `parallel` simultaneous POSTs (within ≤1 ms of each other),
preceded by ≥90 s of complete silence so the IP is "cold". Counted as `blocked` if any
response was `202`.

| `parallel` | OK   | Blocked | First blocked index |
| ---------: | ---: | ------: | :------------------ |
|          1 |    1 |       0 | —                   |
|          5 |    5 |       0 | —                   |
|          8 |    8 |       0 | —                   |
|          9 |    7 |       2 | 7th and 8th of round |
|         10 |    9 |       1 | 9th of round         |

Conclusion: the cold-start burst threshold sits at **8 simultaneous starts**. Anything ≥ 9
will produce at least one `202` and put the IP into the soft-block state. The threshold is
sharp: 8 passes 100 %, 9 fails reliably (n=2 trials in this session).

Once any single response in a round is `202`, the IP is in soft-block and **all subsequent
requests** in the same and following rounds also return `202` until cooldown expires (see
§5).

## 3. Sustained-rate ceiling

Method: serial POSTs spaced by `--interval-ms` of OS sleep between request *ends* (so the
inter-start spacing is `interval_ms + previous_request_duration`).

| `interval_ms` | Effective inter-start | OK  | Blocked | First block |
| ------------: | --------------------: | --: | ------: | :---------- |
|         2 000 |             ~2.7–2.9 s |  10 |       0 | —           |
|         1 500 |             ~2.3–2.4 s |  30 |       0 | —           |
|           500 |             ~1.3–1.5 s |   7 |      23 | 7th request, t≈10 s |

Conclusion: the sustained-rate threshold is bounded by

- safe at ~**2.3 s inter-start** (1 500 ms sleep) over at least 30 requests / 70 s,
- breaks at ~**1.4 s inter-start** (500 ms sleep) within ~10 s.

The 500 ms run failed at the **7th** request — the same number as the cold burst threshold.
This is consistent with a single underlying mechanism rather than separate burst- and
sustained-rate gates: DDG appears to be running a leaky-bucket / sliding-window counter with
a capacity of about 8 starts and a refill of roughly one start every 1.4–1.5 s, applied to
the IP. Whether the 8 starts arrive in 1 ms (parallel burst) or in 9 s (500 ms-spaced
serial), the 9th hits the empty bucket.

Designing for a constant ≥ ~1.5 s inter-start spacing satisfies both burst- and sustained-
rate constraints simultaneously. We add a margin and use **2.0 s** as the
implementation default ([§5 below](#5-implications-for-the-rate-limit-guard)).

## 4. Recovery time

Method: after a soft-block was triggered (parallel-10 burst), single POSTs were issued every
`probe_interval_s` seconds until one returned `200`.

| Probe interval | Time-to-first-200 (from last-blocked response) |
| -------------: | :---------------------------------------------- |
|           10 s | 5 attempts × 10 s ≈ **40–50 s** while probing   |
|            ∞ s | (silent wait) 120 s of silence then 1/1 OK ≥ recovered |

Behaviour:

- Each probe arriving while still under cooldown returns `202` and (per the upstream `ddgr`
  field report) extends or refreshes the cooldown. After 5 consecutive `202` probes (≈ 50 s
  elapsed), the next probe started receiving `200`. Net: **≈ 60 s to clear if you keep
  probing**.
- A full silent wait of 120 s followed by a single probe always returned `200` cleanly.
  We did not narrow the silent-cooldown window further in this round; the existing
  field-report figure of "~20 s if silent" is consistent with our data but not directly
  re-measured. Treat 60 s as a safe upper bound and leave 20 s as an aspirational lower
  bound.

For the implementation we adopt **60 s as the first-block cooldown**. The block is a soft
signal; if our throttler keeps quiet for 60 s, every observation says the next request will
clear.

## 5. Implications for the rate-limit guard

The constraint stated in the user requirement is "no matter how many requests run in
parallel or in bulk, never hit the 202 rate limit". From §2–§4 the necessary and sufficient
conditions are:

1. **At most one DDG request in flight per egress identity (state-file scope) at a time.**
   Bursts of ≥ 9 reliably blow past the bucket. Any cross-process scheduling that allows two
   CLI invocations to fire concurrently is a bug.

2. **Inter-start spacing of ≥ ~1.5 s.** Anything tighter eventually blocks even when serial.
   We use **2.0 s** in code as a 33 % margin.

3. **On a soft-block, hold quiet for ~60 s before the next attempt.** Probing during cooldown
   only extends it.

4. **Permanent slowdown after a recent block.** The very fact that the IP just got 202 is
   evidence that our spacing or burst control was insufficient (or DDG's threshold has
   shifted). Doubling the inter-start spacing for the next ~10 minutes after any block, and
   ratcheting back to baseline only after the 10-minute window expires with no further
   blocks, gives DDG generous headroom to forget about us.

5. **Empty `User-Agent` is mandatory.** Browser-shaped UAs without the rest of the browser
   signal envelope (TLS, JS, header order) escalate to `HTTP 403` with multi-minute hard
   blocks per the upstream `ddgr` issue tracker. We did not re-measure that in this round
   (it would consume our budget on a known-bad path), but the §7.2 default of empty UA is
   carried forward.

The §8 algorithm has been rewritten around (1)–(4); see [`spec.md` §8.1](spec.md#81-algorithm)
for the canonical statement and `crates/duckduckgo-core/src/rate_limit/` for the implementation.

## 6. Reproducing the measurements

```sh
# Single sanity request (must return 200)
cargo run --example ddg_probe --release -- preview --label sanity \
  --out runs/sanity.jsonl

# Cold burst threshold (run with ≥ 90 s silence between scenarios)
cargo run --example ddg_probe --release -- burst --parallel 5  --rounds 1 --label burst_5
sleep 90
cargo run --example ddg_probe --release -- burst --parallel 8  --rounds 1 --label burst_8
sleep 90
cargo run --example ddg_probe --release -- burst --parallel 10 --rounds 1 --label burst_10

# Sustained rate
sleep 90
cargo run --example ddg_probe --release -- serial --interval-ms 1500 --count 30 --label serial_1500
sleep 90
cargo run --example ddg_probe --release -- serial --interval-ms 500  --count 30 --label serial_500

# Recovery time
cargo run --example ddg_probe --release -- recovery --probe-interval-s 10 --max 18 --label recovery_after_burst
```

Each scenario emits one JSON line per request and a final `"phase":"summary"` line. Pipe to
`--out FILE.jsonl` for offline analysis.

When DDG starts blocking and the cooldown is uncomfortably long, rotate the egress IP. With
Cloudflare WARP installed locally:

```sh
warp-cli disconnect && sleep 5 && warp-cli connect
```

Wait for the new connection to come up, confirm with `curl https://api.ipify.org`, then
re-run the scenarios. The new IP starts cold; burst thresholds should reproduce.

## 7. Caveats and what would change the numbers

- **Different egress** (residential vs. datacenter, different country) will likely shift the
  thresholds. KR/SK-Broadband consumer IPs got an 8-start cold bucket on this day; a
  datacenter IP (AWS, GCP, Hetzner) may receive a stricter limit and harder responses.
- **DuckDuckGo can change the limits at any time.** This is not a published API. Our role
  is to use a guard that is conservative enough to absorb modest tightening without silent
  blocking.
- **Other queries / kl regions** were not surveyed in this round. The shape of the 202 body
  did not vary across our `q=rust programming language` calls; nothing suggests a
  per-query gate, but a high-cost query could plausibly cost more than one bucket token.
- **Bursts of `200` no-results** were not seen in our run; the upstream `ddgr` tracker
  notes 200 anomaly pages occasionally. The classifier handles them via the `anomaly_modal`
  body marker.
